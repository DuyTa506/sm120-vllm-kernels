No serving launch or gain claim. Generated overlay hooks raw CT parameters before current scalar preparation, creates a separate indexed Humming state, and dispatches only exact M1024/H2048/top8/E256/TP1/EP1/DP1/SILU/BF16. Other shapes retain current scalar behavior. Both default-off flags are registered in actual vLLM compile_factors; CPU test verifies OFF→ON→probeON→OFF distinct values, CUDA uninitialized. Existing actual-checkpoint audit covers120 projection-scale contracts across40layers and all gate/up global equality; startup additionally asserts each converted layer contract. Input calibration, RN headers and genuine serving ForwardContext are preserved.

**Material memory cost:** duplicate packed weights plus local scales alone estimate16.875GiB across40layers, plus per-layer scratch and conversion peak. This can reduce KV capacity substantially. Adapter records actual perlayer allocated delta, retained storage, workspace shapes and synchronized setup time; these are not yet measured. Keep separate weights until exact layout equivalence is proved. No assumption that micro gains outweigh reduced KV capacity.

Storage audit of installed humming0.1.17: config.py168 `use_flat_weight` is true for4/4 on SM120. transform.py350–365 transforms payload `[E,N/64,64,Kchunks,4]` into `[E,Kchunks,N/64,64,4]`; equal bitwidth does NOT imply unchanged physical layout. Thus FC2 cannot simply alias scalar row-major payload. FC1 additionally differs in gate/up row order. Humming local SFs use int32-group transpose for blockscale vec4 (transform.py500–513); FI retains128×4 swizzled physical storage with strided MMA views (`flashinfer/cute_dsl/utils.py367`). These are nonidentical address mappings. Scalar/global values are tiny and potentially shareable; no meaningful multi-GiB saving is currently established. Changing either kernel's operand layout is a new unmeasured kernel experiment, not an alias optimization.

Do not expand guard or shrink chunkedprefill simply to manufacture activation. First collect actual MoE token-bucket counts under existing tasks, then decide whether exact1024 eligibility is worth this memory cost. A dedicated1024 request can prove dispatch but not representative benefit.
